# ICT.H212 解答書式チェック

「オートマトンと言語」の解答ファイルの形式だけを検査する、Rust / WebAssembly の Web ツールです。解答の正誤、文法やオートマトンの意味、最小性は判定しません。

課題を選び、`.txt` を読み込むか貼り付けると、行番号つきの診断、修正案、SHA-256 を確認・コピーできます。修正案は UTF-8・BOMなし・LF の `.txt` としてダウンロードできます。検査・整形・ハッシュ計算はすべて端末内で行います。解答の送信、アクセス解析、ブラウザへの永続保存、外部 CDN はありません。

## 対応課題

| 課題 | 検査する書式 | 検査しないもの |
| --- | --- | --- |
| 演習01 | 区切り、1-1・1-3 の ASCII、空白・改行・コメント | 答えの語、導出の妥当性、1-2 の文章内容 |
| 演習02 | ASCII、`->`、`$` の空列表記、`|` 不使用、1行1規則、ASCII 辞書順 | 使用記号の正しさ、生成する言語、書き換えの最小性 |
| 演習03 | 区切り、ASCII、カンマ区切りの最終状態とその辞書順、`(S,a,A)` 形式の三つ組と遷移行の辞書順、3-3 の1行の PNG ファイル名 | DFA の意味・最小性、状態の存在・受理条件、画像内容・添付 |

講義資料で必須の UTF-8・区切り・設問別の制約はエラーとして扱います。コメントの残存、BOM、空白・空行は注意として表示します。資料では `###` 注意書きを残すことが許可されています。LF・末尾改行の統一は本ツールの整形方針です。

`.txt` 読込では元のバイト列を検査し、不正な UTF-8 を置換して処理しません。貼り付け・編集後は元ファイルの文字コードや改行コードを確認できません。上限は 1 MiB です。

## 修正案

- UTF-8 BOM と全行コメント（行頭の空白の後に `#` がある行も含む）を除去し、改行を LF に統一。
- 解答欄の端の空行、列挙欄の空行、文章欄以外の行頭・行末の半角空白・タブを除去。
- 演習02の生成規則、演習03の最終状態のリストと遷移行をそれぞれ ASCII 辞書順に並べ替え。重複要素は削除しない。三つ組内の `#` は保持。
- 1-2 の文章内の空白・段落、1-3 の導出順序を保持。最終状態と遷移の間は空行1つ。
- 全角→半角、矢印→`->`、行中の空白除去など、解答の文字を変える変換はしない。
- 欄間は空行1つ、末尾は LF 1つ。氏名・学籍番号は提出用の修正案に保持。

区切りの破損、課題違い、重複・欠落・順序違い、未認識の欄外テキスト、不正 UTF-8 など、解答欄を確定できない入力では修正案とハッシュを生成しません。ASCII 違反などが残る場合は修正案のハッシュを表示しますが、エラーが残っている旨を表示します。「修正案を再検査」で確認してください。

コピペ後の保存設定によって文字コード・改行が変わる場合があります。提出直前の `.txt` を再読込して検査できます。

## SHA-256 の固定仕様：`answer-text-v1`

1. 修正案から、解答欄外の氏名・学籍番号とコメントを除く。
2. 設問番号・区切りをテンプレートどおりに含め、欄間に空行1つを置く。
3. UTF-8、BOMなし、LF、末尾 LF ちょうど1つでバイト列を作る。
4. SHA-256 を64桁の小文字16進数にして表示する。

対象テキストとバイト数を画面で確認できます。新規課題を追加しても既存のハッシュ仕様を変えないでください。氏名・学籍番号の値、コメント、BOM、改行コードの違いはハッシュに影響しません。異なる設問への解答の移動はハッシュに影響します。ハッシュは修正後のテキストに対するものです。

## 開発

Rust 1.98.1、Trunk 0.21.14 を使用します。ツールチェーン・依存は `rust-toolchain.toml` / `Cargo.lock` に固定します。

```sh
rustup target add wasm32-unknown-unknown
cargo install trunk --version 0.21.14 --locked
cargo test --locked -p answer-checker
cargo fmt --all -- --check
cargo clippy --locked --workspace --target wasm32-unknown-unknown -- -D warnings
trunk build
trunk serve
```

`http://localhost:8080` で開きます。配信するのは静的ファイルのみで、開発サーバーに解答を送る処理はありません。クリップボードは HTTPS または localhost で利用してください。コピーが許可されない場合は表示欄を手動選択できます。

Windows で環境変数 `NO_COLOR=1` により Trunk が失敗する場合は、PowerShell で `$env:NO_COLOR='true'` を設定して実行してください。

```sh
trunk build --release --locked --public-url /univ-2026-ICT.H212-normalizer/
```

## 毎回の検証器追加

1. 課題の指示と未記入のテンプレートから、形式のルール・根拠・未確認事項を整理する。
2. `crates/checker/src/assignments/` に課題モジュールを追加し、`mod.rs` の一覧に登録する。共通ルールを再利用し、個別の検査関数は `Section.validate` に登録する。通常の課題追加では共通処理・画面を変更しない。
3. ダミー解答で正常形式と形式違反のテストを追加する。正答そのもの、個人情報、学生の実解答はコミットしない。
4. 共通処理を変えた場合は既存の全課題とハッシュの不変性を検証する。資料にない構文や意味の制約を推測で追加しない。
5. 差分を確認して commit・push。`main` への push で GitHub Actions がテスト・静的ビルド後に GitHub Pages へデプロイする。

LLM はこの開発作業に利用します。Web ツールに LLM API、実行時のコード生成、利用者による検証コードの評価実行はありません。

## 構成

- `crates/checker`: ブラウザに依存しない Rust 検査・整形・ハッシュ処理とテスト。
- `crates/checker/src/assignments`: 課題別の形式定義・検証ルール。
- `crates/web`: Yew のブラウザ画面、ファイル入力、クリップボード。
- `index.html` / `styles.css`: ページ設定とレスポンシブな表示。
- `.github/workflows/pages.yml`: PR の検査と `main` の自動デプロイ。

初期ルールの出典は提供された `autolang第1回.pdf` 15–16ページ、`01_answer-sheet.txt`、`02_answer-sheet.txt`、`03_answer-sheet.txt`、追加提供の三つ組記法の図。最終状態のカンマ区切りとソートはユーザーの指定です。資料・実解答はリポジトリに含めていません。
