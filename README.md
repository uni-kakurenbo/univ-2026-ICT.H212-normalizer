# ICT.H212 解答書式チェック

「オートマトンと言語」の解答ファイルを検査する、Rust / WebAssembly の Web ツールです。演習01〜07は形式だけを検査します。演習08はユーザーの追加指定により、講義の構成・計算規則も機械的に検査します。一般の言語等価性・最小性や証明の正しさは判定しません。

課題を選び、`.txt` を読み込むか貼り付けると、行番号つきの診断、修正案、SHA-256 を確認・コピーできます。入力・編集・ファイルの読込・課題の変更に合わせて自動更新されるため、検査ボタンを押す必要はありません。修正案は UTF-8・BOMなし・LF の `.txt` としてダウンロードできます。検査・整形・ハッシュ計算はすべて端末内で行います。解答の送信、アクセス解析、ブラウザへの永続保存、外部 CDN はありません。

## 対応課題

| 課題 | 検査する書式 | 検査しないもの |
| --- | --- | --- |
| 演習01 | 区切り、1-1・1-3 の ASCII、空白・改行・コメント | 答えの語、導出の妥当性、1-2 の文章内容 |
| 演習02 | ASCII、`->`、`$` の空列表記、`|` 不使用、1行1規則、ASCII 辞書順 | 使用記号の正しさ、生成する言語、書き換えの最小性 |
| 演習03 | 区切り、ASCII、カンマ区切りの最終状態とその辞書順、`(S,a,A)` 形式の三つ組と遷移行の辞書順、3-3 の1行の PNG ファイル名 | DFA の意味・最小性、状態の存在・受理条件、画像内容・添付 |
| 演習04 | 4-1・4-2 の最終状態と三つ組の構文・各リストの辞書順、4-2 の状態名内の文字順、4-3 の生成規則の構文・行順・記号の付け直し指定 | NFA/DFA の正しさ・決定性・受理言語・部分集合の内容、生成規則と DFA の対応 |
| 演習05 | 最終状態と三つ組の構文・各リストの辞書順、`$` の ε 表記、5-2 の既知の元状態名単位の連結順、`%%%` 注意書き | ε-NFA の構成、ε除去、到達可能性、元の状態との対応、追加状態を含む名前の内部順 |
| 演習06 | 最終状態と三つ組の構文・各リストの辞書順、6-1.2 の組の構文・左右と行の辞書順、6-1.3 の `q1,q2,…` の表記と欠番、`%%%` 注意書き | 遷移関数の全域性、状態 Z の追加、D の要素・組の正しさ、最小性、元の状態集合と番号の対応 |
| 演習07 | 日本語の証明文、指数の `^{...}`、比較記号・所属記号・空語の明確な記法違反、数式らしい表記への warning | 証明の妥当性、反復補題の条件、選んだ語・指数の正しさ、数式範囲や意味の完全な認識 |
| 演習08 | 書式、使用記号、番号条件、3項以上の和を含むボトムアップ構成、linear form の値、K・Delta の更新と終了、トップダウン法の状態・遷移・最終状態、別名 e | 任意の受理語の経路、一般の正規表現同士の言語等価性、講義の規則を超える同値変形 |

講義資料で必須の UTF-8・区切り・設問別の制約はエラーとして扱います。BOM、余分な空白・空行は注意として表示します。コメント行は警告を出さず、修正案とハッシュ対象から自動で除きます。演習08ではスペース・タブが明示的に禁止されているためエラーです。資料では注意書き（演習01〜04は `###`、演習05〜08は `%%%`）を残すことが許可されています。LF・末尾改行の統一は本ツールの整形方針です。

`.txt` 読込では元のバイト列を検査し、不正な UTF-8 を置換して処理しません。貼り付け・編集後は元ファイルの文字コードや改行コードを確認できません。上限は 1 MiB です。

## 修正案

- UTF-8 BOM と全行コメントを除去し、改行を LF に統一。コメントの開始記号は演習01〜04が `#`、演習05〜08が `%%%`（行頭の空白の後も認識）。演習04の最終状態行の `#` は以下の例外で保持。演習05〜08では `#` をコメントとして除去しない。
- 解答欄の端の空行、列挙欄の空行、文章欄以外の行頭・行末の半角空白・タブを除去。
- 演習02・04の生成規則、演習03〜06・08の最終状態のリストと遷移行をそれぞれ ASCII 辞書順に並べ替え。重複要素は削除しない。三つ組内の `#` は保持。
- 6-1.2 は組の左右を ASCII 辞書順にそろえてから各行を並べ替える。例：`(B,A)` → `(A,B)`。重複は保持し、構文が壊れた組の内部は変更しない。
- 1-2・演習07の文章内の空白・段落、1-3・8-1.2.1 の導出順序を保持。最終状態と遷移の間は空行1つ。演習08の出発状態と最終状態は別々の行として順を保持。
- 全角→半角、矢印→`->`、行中の空白除去など、解答の文字を変える変換はしない。
- 欄間は空行1つ、末尾は LF 1つ。氏名・学籍番号は提出用の修正案に保持。

区切りの破損、課題違い、重複・欠落・順序違い、未認識の欄外テキスト、不正 UTF-8 など、解答欄を確定できない入力では修正案とハッシュを生成しません。ASCII 違反などが残る場合は修正案のハッシュを表示しますが、エラーが残っている旨を表示します。「修正案を入力に反映」で修正案を編集欄に戻すと、検査結果も自動更新されます。

コピペ後の保存設定によって文字コード・改行が変わる場合があります。提出直前の `.txt` を再読込して検査できます。

### 演習04固有の記法

4-1 は NFA、4-2 は DFA を同じ三つ組の書式で検査します。最初の解答行が最終状態のカンマ区切りリストで、以降が遷移です。決定性や状態・入力記号の正しさは調べません。

4-1・4-2 の最初の空でない解答行では、`#` 単独、または `#` の直後がラテン大文字・カンマの行を最終状態行として保持します。これにより `#`、`#,A`、`#A,#AB` をコメントとして消しません。書式が壊れた `#A,` なども保持して診断します。`###` 指示行や `# コメント` は除去します。この位置の `#A...` はコメントと区別できないため、注意書きは `###` で始めてください。演習01〜03のコメント・ハッシュ処理は変えません。

4-2 の状態名は元の状態集合の文字を ASCII 辞書順にまとめる指定です。最終状態と三つ組の出発・到着状態について、文字順を検査します（`AB#` はエラー、`#AB` は正しい書式）。状態名の文字を自動で並べ替えると状態を付け替えてしまうため、エラー表示のみで保持します。どの状態集合が正しいかは検査しません。空集合に対応する状態の ASCII 表記は提供資料に指定がなく、独自の記号を定義・要求しません。

4-3 は出発記号 `S` を左辺に含み、他の非終端記号には `A,B,C,…` を飛ばさず使用する指定を検査します（`S` は出発記号として予約）。左辺と `X->xY` の `Y` はラテン大文字1文字です。`->`・`$`・`|` 不使用・1行1規則・行の辞書順は共通検査を再利用します。同じ左辺の `xY` どうしで、終端記号が昇順なのに非終端記号が降順になっていないかを検査します。`S->aB` と `S->bA` は交差としてエラーです。左辺が異なる規則や同じ終端記号どうしは比較しません。これはユーザーに確認した比較範囲です。状態名の変更は自動では行いません。

### 演習05・06固有の記法

注意書きは `%%%` で始まる行だけを除去します。`%%%%` の見出しも含みます。三つ組の内部にある `%` や、`%`・`%%` だけで始まる行をコメントと推測して消すことはしません。指示は課題の形式を確認する根拠として読み、Web ツールが実行する命令としては扱いません。

5-1 は ε-NFA、5-2 は DFA を共通の三つ組の構文で検査します。ε の表記は入力記号の欄全体を `$` にします。`ε`・`ϵ` や `$x` は表記エラーです。ε除去や到達不能状態の削除が正しく行われたかは調べません。

5-2 は `q0`〜`q3`・`r0`〜`r4` を元の状態名として、集合状態名をその名前単位の辞書順で連結します。`q0q2r1` は正しい書式、`r1q0q2` は順序エラーです。文字単位では判定・整形しません。最終状態と遷移の出発・到着状態にこの検査を行います。追加状態の名前や空集合の ASCII 表記は指定がないため、全体を既知の元状態名に分割できない名前は内部順の検査を行わず保持します。この範囲はユーザーに確認済みです。どの元の状態を組み合わせるかや、元のオートマトンの状態とどう対応するかは検査しません。状態名の自動変更は行いません。

6-1.2 は `(X,Y)` を空白なしで1行に1組列挙します。左右と行をそれぞれ ASCII 辞書順に並べます。同じ状態どうしの組や D の要素に該当するかは判定しません。ユーザーの確認により、空欄は0件の組のリストとして許可します。空集合を表す特別な文字列は要求しません。他のオートマトン欄は空欄を未回答として検出します。

6-1.3 の状態名は、小文字 `q` と1以上の整数で `q1,q2,…` と表記し、`q0`・`q01`・`Q1` はエラーです。記載された状態名に `q1` からの欠番がないかも検査します。最終状態や遷移行の辞書順は数値順ではないため、`q1,q10,q2,…` となります。元の状態集合のソートと各番号の割り当て、状態 Z の追加、遷移関数の全域性、オートマトンの最小性は検査しません。状態名を自動で付け替える処理もありません。

### 演習07の数式候補

証明文は日本語を許可し、文章全体への ASCII 制限はかけません。数式の区切りはテンプレートにないため、ユーザーの指定に従い自動で検出できる部分だけを扱います。数式範囲を登録する UI や、提出ファイルに加える補助記号はありません。

`≤`・`≠` などの比較記号、`∈`・`∉`、空語の `ε`・`ϵ` は明示された記法に反するためエラーです。ASCII の底に続く `x^k`、閉じ括弧のない `x^{k`、空の `x^{}` もエラーとして検出します。記法は `^{...}`、`eps`、`|u|`、`in` / `not in`、`<=`・`>=`・`<`・`>`・`=`・`!=` です。

ギリシャ文字、上付き・下付き文字、Unicode の数式用英数字、全角の英数字、矢印、LaTeX コマンド、`$`、日本語を含む指数・長さの候補などは、文章中の記号と断定できません。「数式の誤表記である可能性があります」という warning にとどめます。これは補助的な検出であり、すべての数式範囲や誤表記を認識するものではありません。数式の文字や証明文の内部は自動変更しません。証明内容、反復補題の適用、例として選んだ語や指数は検査しません。

### 演習08固有の記法

8-1.1・8-1.2.2 の最初の解答行は出発状態1つ、次の解答行はカンマ区切りの最終状態、それ以降が三つ組の遷移です。修正案は出発状態と最終状態を連続する別々の行に置き、遷移の前に空行1つを置きます。出発状態を並べ替えの対象に混ぜません。最終状態と遷移は数値順ではなく ASCII の文字順で並べ、`11` は `2` より前になります。

8-1.1 は正の整数表記（余分な先頭0なし）、記載された状態名の1からの連続使用、最大番号の1状態だけが最終状態であることを検査します。この番号規約はユーザーに確認済みです。番号を自動で変更する処理はありません。

ユーザーの追加指定により、`aac`・`bbc`・`cbaa` の受理経路も番号の検査対象にします。出発状態・最終状態・ε遷移の前後をすべて含めた状態列で、各経路の厳密な単調増加、`aac` と `bbc` の経路長の一致と各位置の `Si <= S'i`、`bbc` と `cbaa` の `n < m` と `i < n` の位置の `Si <= S'i` を検査します。任意の受理語への単調増加は `*` による状態の再訪と両立しないため、対象をこの3語に限定することをユーザーに確認済みです。

「戻る経路は考えていない」というユーザーの意図を、同じ状態を再訪しない受理経路を対象にする解釈で扱います。番号の大小で辺を除外すると番号付けの違反を隠してしまうため、番号が減少する辺自体は除外しません。語ごとに候補の状態列が一意のときだけ番号を比較し、候補が0本・複数の場合は該当条件を未検査として注意表示します。ε遷移の位置が違っても状態列が同じなら1候補と扱います。同一の三つ組の重複は経路の分岐として数えませんが、入力と修正案から削除はしません。探索は反復処理で行い、1語あたり100,000ステップ（辺の調査と状態列の比較）の上限に達した場合も未検査を明示します。診断だけを追加し、状態名・遷移・修正案・ハッシュの生成仕様は変更しません。

8-1.1 の構成は、問題文の正規表現を構文木として読み、講義の和・積・`*` の規則から作る匿名の構造テンプレートと照合します。3項以上の和では共通の入口・出口を1組だけ設けて全項を直接 ε 分岐・合流させます。状態数・遷移数の必要条件だけで済ませず、出発・最終状態、辺のラベルと接続先全体を照合します。状態番号や和の項の並びの違いは許容します。入力の重複三つ組は論理的に同じ1辺と扱いますが、修正案からは削除しません。固定の正解解答ファイルを保持したり、正解の番号・辺を画面に提示したりはしません。

入力記号は `a,b,c`、ε 遷移は `$` に限定します。8-1.2 の正規表現は `a,b,c`、連結、`+`、`*`、半角括弧、定数 `0`・`1` と全体の別名 `e` を使います。課題の正規表現全体を展開して書く場合や、他の式に `e` を埋め込む場合も診断します。括弧を含む状態名を三つ組や最終状態欄で扱えます。

8-1.2.1 は `lf(p)={<x,q>,<y,r>}`（空集合は `lf(p)={}`）の行を先に記載し、続けて `i=0,K={...},Delta={...}` の各段階を0から順番に記載します。書式に加え、講義の再帰規則で `lf(p)` を計算して値を照合します。初期値 `K_0={}`・`Delta_0={e}`、`K_{i+1}=K_i∪Delta_i`、次の `Delta`、処理する式の `lf` 行の存在、`Delta` が空になるまでの反復と終了後の余分な段階も検査します。積の規則では空列を含む左項の場合に右項の linear form も加えます（講義9–10ページの計算例に従う）。linear form の行、組や集合内の要素、各段階の行は自動で並べ替えず、重複も保持します。

ユーザーの推奨方針として、`lf(p)=...` の行どうしと各行内の `<記号,正規表現>` の組を、それぞれ文字列全体の ASCII 辞書順で検査し、降順の箇所を warning にします。講義の必須条件としてのエラーにはしません。空集合・1件・同一項目の重複は順序違反にせず、構文が壊れた行は構文エラーだけを扱います。`i=...` の段階順や `K`・`Delta` の集合内の順序には、この推奨検査を適用しません。自動並べ替えを加えないため、修正案と `answer-text-v1` のハッシュ仕様も維持します。

8-1.2.2 は出発状態が `e`、各状態の出辺がその `lf(p)`、最終状態が空列を含む式の集合であることを検査し、出発状態から到達しない余分な状態も診断します。内部比較では冗長な括弧、和・積の結合、和の項順・重複、`0`・`1` の基本恒等式を整理します。一般の正規表現の言語等価性を判定する処理ではないため、講義の再帰規則から得る式を基準にします。式の長さ・深さや計算・構造探索の上限に達した場合は、該当検査が未完了であると注意表示します。診断に計算結果の正解は提示せず、修正案・ハッシュの生成仕様も変更しません。

## SHA-256 の固定仕様：`answer-text-v1`

1. 修正案から、解答欄外の氏名・学籍番号とコメントを除く。
2. 設問番号・区切りをテンプレートどおりに含め、欄間に空行1つを置く。
3. UTF-8、BOMなし、LF、末尾 LF ちょうど1つでバイト列を作る。
4. SHA-256 を64桁の小文字16進数にして表示する。

対象テキストとバイト数を画面で確認できます。新規課題を追加しても既存のハッシュ仕様を変えないでください。氏名・学籍番号の値、コメント、BOM、改行コードの違いはハッシュに影響しません。異なる設問への解答の移動はハッシュに影響します。ハッシュは修正後のテキストに対するものです。

## 開発

Rust 1.98.1、Trunk 0.21.14 を使用します。ツールチェーン・依存は `rust-toolchain.toml` / `Cargo.lock` に固定します。

```sh
rustup target add wasm32-unknown-unknown
cargo install trunk --version 0.21.14 --locked
cargo test --locked -p answer-checker
cargo fmt --all -- --check
cargo clippy --locked --workspace --target wasm32-unknown-unknown -- -D warnings
trunk build
trunk serve
```

`http://localhost:8080` で開きます。配信するのは静的ファイルのみで、開発サーバーに解答を送る処理はありません。クリップボードは HTTPS または localhost で利用してください。コピーが許可されない場合は表示欄を手動選択できます。

Windows で環境変数 `NO_COLOR=1` により Trunk が失敗する場合は、PowerShell で `$env:NO_COLOR='true'` を設定して実行してください。

```sh
trunk build --release --locked --public-url /univ-2026-ICT.H212-normalizer/
```

## 毎回の検証器追加

1. 課題の指示と未記入のテンプレートから、形式のルール・根拠・未確認事項を整理する。
2. `crates/checker/src/assignments/` に課題モジュールを追加し、`mod.rs` の一覧に登録する。テンプレートどおりの `comment_prefix` を指定する。共通ルールを再利用し、個別の検査関数は `Section.validate` に登録する。通常の課題追加では共通処理・画面を変更しない。
3. ダミー解答で正常形式と形式違反のテストを追加する。正答そのもの、個人情報、学生の実解答はコミットしない。
4. 共通処理を変えた場合は既存の全課題とハッシュの不変性を検証する。資料にない構文や意味の制約を推測で追加しない。
5. 差分を確認して commit・push。`main` への push で GitHub Actions がテスト・静的ビルド後に GitHub Pages へデプロイする。

LLM はこの開発作業に利用します。Web ツールに LLM API、実行時のコード生成、利用者による検証コードの評価実行はありません。

## 構成

- `crates/checker`: ブラウザに依存しない Rust 検査・整形・ハッシュ処理とテスト。
- `crates/checker/src/assignments`: 課題別の形式定義・検証ルール。
- `crates/web`: Yew のブラウザ画面、ファイル入力、クリップボード。
- `index.html` / `styles.css`: ページ設定とレスポンシブな表示。
- `.github/workflows/pages.yml`: PR の検査と `main` の自動デプロイ。
